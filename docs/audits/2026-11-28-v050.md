# v0.5.0 native implementation recheck — 2026-11-28

## Scope and evidence boundaries

The reviewed baseline is `8af7500d8b26dc5aa3b7209ced8a8173bef7ae61` in
[`KiaroSama/Grammers-Secret-Chat`](https://github.com/KiaroSama/Grammers-Secret-Chat),
formerly `Telethon-Secret-Chat`. The native v0.5.0 implementation was restored
after the owner merged [PR #53](https://github.com/KiaroSama/Grammers-Secret-Chat/pull/53).
This review covers those newly restored execution paths and their interaction
with the existing core. It does not replace the earlier audit with an assumption
that all its findings recurred.

The finite acceptance set below covers native protocol ordering and rekeying,
durable and protected storage, migration, native media authorization, export file
publication, executable historical tests, current CI evidence, and standalone
maintenance commands. All protocol and media reproductions use local synthetic
keys and data; the SDK fixture uses its offline runner.

The baseline's green release jobs actually executed 480 passing first-party
tests with 2 ignored cases on Linux, and 466 passing tests with 5 ignored cases
on Windows. Separately, the historical mapping listed 1851 identities, of which
1731 pointed into 87 absent integration files. A mapping is not an execution
record. No live Telegram interoperability or protected signing claim follows
from these offline results.

[`784443dd0abdea12b9a51dfe6623c246dd409ed4`](https://github.com/KiaroSama/Grammers-Secret-Chat/commit/784443dd0abdea12b9a51dfe6623c246dd409ed4).

## Confirmed findings and implemented repairs

### F01 — Rekey authentication boundaries were lost across gaps and restart

**Impact: high, protocol state integrity.** The native receiver retained a
preceding shared key while any gap existed, but did not retain which key had
authenticated each buffered message or the incoming sequence where a key
transition became mandatory. It accepted a later preceding-key frame after a
new-key frame established the transition. A conflicting key for an already
buffered sequence was treated as a duplicate. Later current-key gaps prolonged
old-key retention. Serializing and reopening did not restore a missing boundary.

CommitKey also needs its own boundary: the matching commitment is authenticated
under the preceding key, and subsequent messages use the new key. A delayed
commitment can establish an earlier transition than a subsequently received
new-key message. Remembering only the current pending exchange loses that
information after implicit adoption.

The repair adds `incoming_key_cutover`, `accepted_exchange`, and
`gap_key_fingerprints` to native `Chat`, with strict, default-compatible
serialization. `src/rekey/provenance.rs` checks the authenticated fingerprint
before any state publication, records every buffered frame's provenance,
rejects a conflicting buffered identity, and derives the earliest proven
transition from new-key traffic or a matching commitment. A commitment must
authenticate with the preceding key and declare the expected new fingerprint.
The receive transaction refuses buffered or arriving preceding-key messages at
or beyond the transition. The original public `Envelope` layout stays intact.

`rekey::adopt` preserves the accepted exchange identity before clearing pending
state. Retirement waits for the incoming sequence range preceding the transition,
rather than all future gaps. The `previous_key.is_some()` retirement guard also
prevents a confirmation flag from a completed exchange from erasing the next
exchange's deferred commitment boundary. Queue drain, close, and protected-mode
scrubbing remove corresponding provenance. Restored snapshots validate the same
invariants before being accepted.

**Compatibility:** a legacy single-key gap has an unambiguous current-key origin
and remains readable. A legacy snapshot containing both a preceding key and gaps
without provenance is ambiguous and is refused without rewriting it. Do not
"repair" that snapshot by guessing fingerprints or discarding obligations.
Preserve the original file for an explicitly authorized recovery procedure.

**Acceptance:** `tests/support_v050/protocol.rs` covers future old-key input,
pre-buffered conflicts, conflicting duplicate keys, persisted boundaries, delayed
commitments, the wrong authentication key on a commitment, stale confirmation
flags, and retirement while later new-key gaps remain. A positive control runs
all 24 arrival permutations of four messages, reopens serialized state after
every arrival, delivers exactly the expected messages, and retires the old key.

### F02 — Buffered ACK and layer order was checked too late

**Impact: high, protocol effects before rejection.** Header preflight compared a
new frame only with processed watermarks. It did not compare buffered predecessor
and successor headers. An authenticated Resend behind a gap could therefore
schedule transmission before its contradictory ACK or layer order was noticed
when that gap eventually drained. Invalid buffered order could also survive
native snapshot validation.

`sequence::preflight_header` now checks both nearest buffered neighbors before
immediate Resend handling. ACK and layer values must remain nondecreasing in
sequence order, and ACK cannot exceed the actual outgoing count. The separate
`validate_pending` path applies equivalent ordered checks to restored gaps.
Parity checks and the existing replay behavior for already processed messages
are preserved.

**Acceptance:** tests reject successor ACK contradictions before any retransmit,
reject buffered layer regression on arrival, and refuse nonmonotonic restored
gaps. Valid out-of-order traffic remains covered by the permutation/restart test
and the restored sequence and resend suites.

### F03 — The last representable sequence position was rejected

**Impact: medium, terminal counter correctness.** Native validation and counter
increment filters confused a raw sequence index with the count after accepting
that index. The final valid signed 32-bit wire position could not be sent or
received.

`MAX_SEQUENCE_COUNT = i32::MAX / 2 + 1` is now the accepted terminal count.
Chat validation, outgoing preparation, and incoming acceptance use that count.
Checked wire conversions still reject the next unrepresentable operation.

**Acceptance:** terminal incoming and outgoing cases each succeed once, preserve
coherent state, and refuse the next operation. No wrapping arithmetic or relaxed
parity rule is introduced.

### F04 — Persisted duplicate identities silently replaced obligations

**Impact: high, durable data loss.** Default JSON deserialization into ordered
maps selected the last value for duplicate keys. A second chat entry could
replace its pending outbox; a second outbox entry could turn a pending frame into
a nonpending one. The same ambiguity reached historical binding migration and
the authenticated inner state of encrypted ingress storage. Authentication of
bytes does not establish uniqueness of their logical identities.

`src/storage/strict.rs` adds typed unique-map and unique-set visitors. They check
identity after key deserialization, so numeric aliases such as `7` and `07` also
collide. These visitors cover native chats, settings, private records, outbox,
gaps, ordinary and service deliveries, key-provenance metadata, custody controls
and age maps, ingress applied identities, and autosave pending downloads. Autosave
validates numeric identity before returning its existing public string-key map.
Private record decoding also rejects trailing JSON input.

All readers and migrations refuse ambiguous state before normalizing or writing
it. Custody resume preserves the prior in-memory state on failure. Autosave
settlement does not rewrite an invalid pending journal. Valid unique legacy
records retain their documented optional-field defaults, and unknown structured
fields remain rejected.

**Acceptance:** the 11 persistence cases under `tests/support_v050/durability.rs`
and `durability_schema.rs` cover ordinary/native/encrypted restore, historical
migration, exact duplicate and numeric alias identities, pending settlement,
custody open and resume, and valid-state controls. Rejection tests compare the
original file bytes after the failed operation.

### F05 — A data file could be accepted as the lock sidecar

**Impact: high, exclusive-owner assumption.** The native lock opener accepted an
existing nonempty regular file. If the sidecar aliased the snapshot inode, an
atomic snapshot replacement moved the lock to an obsolete inode and could admit
a second apparent owner. This is distinct from the already covered symlink case.

After acquiring the lock, native `FileStorage` now requires its sidecar to be an
empty regular file. It rejects invalid objects without truncating them. Existing
platform-specific locking, private permissions, and atomic snapshot publication
remain in place.

**Acceptance:** tests refuse a data file as a lock and exercise a sidecar alias
across atomic replacement. They retain valid empty-sidecar behavior and require
the original data to remain unchanged. Existing lock, permission, symlink,
replacement, and restart suites continue to be required.

### F06 — Native media noticed session changes after side effects

**Impact: high, authorization and destination integrity.** The native adapter
checked its verified account binding only before and after an entire transfer.
When a synthetic home-DC authorization key changed while the first chunk awaited
completion, RAM download, disk download, and upload still dispatched a second
chunk. Disk download replaced an existing destination before returning
`Authorization`. The older core's equivalent control correctly stopped after
the first chunk.

The adapter now passes a retained binding guard into native transfer helpers.
Downloads check it before and after each awaited chunk, before plaintext release,
and in the blocking worker immediately before atomic publication. RAM plaintext
stays zeroizing until the final binding check. `IoTracker` and cancellation
ownership remain intact. Public unbound media helpers keep their API through
compatibility wrappers; the verified transport uses guarded variants.

`src/media/upload.rs` provides per-part checks around actual SDK invocations.
It preserves streaming encryption, the small-file checksum, the 512 KiB part
size, and four bounded producers for large uploads. Guarding only the outer SDK
upload future would leave the original defect. Requests already dispatched
before a binding change cannot be revoked; this remains the documented boundary.

**Acceptance:** the real SDK offline fixture pauses the first of two chunks,
changes a synthetic authorization key, and requires one-call refusal with the
preexisting destination intact. Disk, RAM, and upload each have unchanged-binding
controls; the older core provides an independent comparison. Existing worker
drain and cancellation tests are retained.

### F07 — Export downloads published truncated or oversized files as complete

**Impact: high, exported data integrity.** A declared 65-byte document was
reported as successful when a local SDK response supplied 16 or 96 bytes. The
implementation wrote before checking length and accepted either a short response
or `offset >= size`. Partial attempts could damage a destination or contaminate
a file-reference refresh retry.

`GrammersExportClient` now computes cumulative length with checked arithmetic
before writing. Every response must fit the requested 128 KiB chunk. A known
size must complete at exact equality; early EOF and excess bytes fail. A size of
zero remains explicitly treated as unknown size, preserving that API convention.

`LazyFile` can stage an attempt in a sibling temporary file. Only successful
flush, sync, and final validation publish it. `finish` is idempotent so the
adapter and higher-level file pipeline can both finalize safely. A borrowed
download attempt's drop guard removes staging even if its future is cancelled
while the caller retains the `LazyFile`. Refreshed references restart from an
empty attempt. Inline contents use the same complete-publication discipline.
Completion counts and cache entries are updated only after success.

**Acceptance:** standard SDK fixture cases cover exact single and multiple
chunks, short and oversized responses, a second-chunk early EOF, RPC failure,
empty and nonempty unknown-size files, repeated finish, cancellation and reuse.
Ordinary export tests cover partial reference refresh and unavailable-file
cleanup. Refusal preserves sentinel destination bytes and leaves no staging
artifact.

### F08 — Historical tests were missing and CI did not enforce current identities

**Impact: high, verification regression.** The baseline retained historical
mapping claims but omitted 87 executable `tests/rust_*.rs` files and six export
support files. `migration-audit --require-complete` could report completion from
mapping data alone. The current matrix verifier also confused three collected,
explicitly ignored Windows filesystem-contract cases with tests excluded at
compile time, and the final Rust CI gate did not run current identity verification.

The repair restores executable wrappers and support from repository history,
adapting fixtures to the current SDK without dropping assertions. Dormant SDK
fixtures now derive full v2 tags from their original synthetic clients instead
of calling the intentionally refused v1 constructor. Typed synthetic authorization
and configuration replies preserve the existing real-client verification path. It restores
the associated export/live documentation and the standalone generator contract.
`migration/current-rust-cases.json` is populated from actual collected test
identities. Historical mapping and current execution have separate policies and
truthful messages. The migration audit requires every historical mapped identity
to exist in the current inventory; execution proof remains the matrix gate.

The aggregate Rust CI job downloads all seven test logs plus the Linux verifier
archive from its own workflow run. It verifies both archive checksum layers and
the embedded exact commit before running `matrix-evidence` against the reviewed
current inventory. Missing or duplicate tests, unexpected ignores, malformed
summaries, missing matrix legs, and nonzero failures remain failures. Collected
Windows ignores cannot be relabeled as absent. Platform compile exclusions are
explicit and separate from live tests.

Independent review also caught a gap in the proposed exclusion policy: an
ordinary identity could be excluded on all seven legs while remaining in the
mapping. A direct CLI reproduction returned success for that never-executed
identity. The final policy requires every non-live identity to remain executable
on at least one leg, with a dedicated refusal regression.

**Acceptance:** synthetic evidence validates legitimate Windows records and
rejects the same ignores on Linux. Restored wrappers must compile and execute;
the final seven real CI records must match the checked-in manifest. Never make
the gate pass by deleting an expected identity, replacing assertions with
constants, broadening skips, or copying another commit's log.

### F09 — The standalone Rust schema generator interface disappeared

**Impact: medium, release-tool compatibility.** The restored generator offered
JSON `--out` output but rejected the existing `--output` Rust-code interface.
The missing packaging tests had previously compiled that generated Rust from a
copied binary after deleting its original source stage.

`generate-schema --output PATH` is restored using the embedded schema and actual
generator. JSON `--out` stays supported. `--check` compares existing output and
does not overwrite a caller's changed file. Packaging fixtures include the data,
assets, current SDK pin, and lockfile needed to compile their actual source.

**Acceptance:** run the copied command outside its checkout, generate and compile
Rust code, verify repeated `--check`, reject modified output without changing it,
and retain JSON generation. All five maintenance commands remain covered by the
source distribution and installed-consumer jobs.

## Verification and maintenance policy

The final PR evidence must identify its current head and distinguish executed
tests, ignored live tests, collected platform ignores, and compile-time platform
exclusions. The project matrix covers Rust 1.95 MSRV and 1.100, Linux and Windows,
x64 and ARM64, debug/release, and the portable AES backend. It also requires
vendored transport tests, standalone scanner tests, documentation, formatting,
clippy, tracked source archives, downstream Git consumption, and installed tools.

The existing daily Cargo and GitHub Actions Dependabot configuration is retained.
The README already has a dynamic semver-sorted repository-tag badge linked to
the repository's tags page. Its value must continue to derive from actual tags;
do not replace it with a manually maintained version badge. The bundled secret
schema inventory, negotiated inner secret-chat maximum 144, and outer SDK layer
234 are different facts; documentation now makes that distinction explicit.

This audit does not claim all possible executions are enumerable. Its closed
acceptance matrix, practical red/green proofs, restored regression suites, and
final-head CI provide reproducible evidence for the reported defects. Live
Telegram tests require the repository's authorized two-account/official-client
harness and remain explicitly ignored in ordinary CI. Signing requires its
protected release environment. Neither is marked passed without that execution.
