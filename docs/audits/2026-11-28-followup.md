## F01 — Implicit TTL could change retry identity and be selected too early

**Impact: medium; unreliable retries and stale outgoing conversation policy.**

Persistent `send_text_with_id(id, random_id, text)` has no caller TTL parameter,
but its retained identity included the current conversation TTL. After an uncertain
send and an authenticated `SetMessageTTL(17)`, repeating the identical public
request after an actual encrypted FileStorage reopen failed with
`random_id is already bound to different message content`.

Both persistent and transient wrappers also read TTL before waiting for the
outbound lock. A deterministically queued send therefore encoded `0` after the
peer's authenticated TTL `17` update had already committed. Telegram permits an
explicit per-message TTL to override conversation TTL; this finding does not label
every overlapping old-TTL message a wire-protocol violation. The wrapper contract
is now precise: **an implicit TTL is selected when a new frame reserves its sequence**.

The original regression run had **3 failures and 1 passing explicit-TTL control**.
No sleeps are used to guess scheduling: a controlled transport blocks the first
RPC, and the next future is polled to its wait boundary before the peer update.

### Implemented repair

- A private `TextTtl::{Explicit, Conversation}` policy separates actual caller
  input from implicit conversation state. Public RAM signatures remain unchanged.
- New implicit identities use a separate text-only hash domain. Explicit RAM
  identity still includes the explicit TTL, and changed text/TTL is refused.
- New implicit TTL is read under the final per-chat state lock, **after** draining
  older pending sends. Reading it merely after the outbound lock is insufficient:
  the pending drain itself may await a peer update.
- Recognized retries return the original frame and retain its random ID, sequence,
  padding, TTL, and ciphertext. No re-encryption or digest rewrite is performed.
- Legacy digests first use their existing current-TTL matching fast path. Otherwise
  the private `retained_outgoing_text_ttl` helper authenticates the retained outgoing
  frame with a held current, previous, or pending key, validates its wrapper and
  counters, checks ID/sequence/text, recovers the TTL, and compares the original
  legacy digest. It never invokes receive processing or changes protocol state.

**Historical limit:** an old retained ciphertext can outlive its encryption key.
If the current-TTL digest does not match and that key has retired, the original
TTL cannot be recovered from its hash alone. The same-ID path fails closed with
fixed, secret-free `retry_pending` guidance. That API remains key-independent and
resends entries still marked pending using their exact retained bytes. Entries
whose RPC already succeeded remain retained for peer acknowledgement and are not
forcibly retransmitted; the call can correctly return `0`. The store and obligation stay
unchanged by refusal. This is an explicit completed fallback, not permission to
guess TTL or accept different text merely because an ID exists.

The existing FileStorage/outbox shapes are unchanged and legacy digests stay intact. New implicit
digests require the updated matcher; downgrading to older code can refuse its
same-ID matching path, although exact `retry_pending` resend remains available.

## F02 — Transient wrappers retained an inaccessible duplicate event queue

**Impact: medium; growing RAM use and unnecessary plaintext retention.**

The prior durable-path fix suppressed events when a checkpoint was present.
Transient wrappers have no checkpoint and expose no way to drain the embedded
RAM manager's queue. Receiving a service and ordinary message, acknowledging an
outbound frame, and closing the chat left **4 inaccessible events** behind.
The baseline regression failed while its direct-RAM positive control passed.

The repair chooses an immutable private `EventRetention` policy at construction.
Persistent and transient wrappers discard duplicate events centrally in `emit`;
direct RAM managers continue to queue them for their public `drain_events` API.
Suppression is independent of whether an individual operation succeeds, fails,
is canceled, or supplies a checkpoint. There is no after-the-fact drain whose
cleanup could be skipped by an early return. Durable receipt/ACK paths are intact.

The new mode tests verify an empty transient queue after the real API sequence
and preserve direct RAM `ChatReady`, `MessageAcknowledged`, service, ordinary
message, and closure categories, including a second empty drain. Existing durable
receipt, cancellation, storage-failure, replay, and event tests remain in the gate.

The earlier A10 covered durable wrappers. It did not cover this transient path;
constructor-level ownership now makes the distinction explicit.

Sources: [central event emission](../../src/manager/delivery.rs) and
[mode construction and event regression tests](../../src/runtime_modes/modes.rs).

## F03 — A normal JPEG thumbnail requested a multi-gigabyte allocation

**Impact: high; process abort while exporting ordinary saved media.**

A valid synthetic `6000 x 4000` RGB JPEG was only **70,690 bytes**, within the
archive's compressed input limit. Both direct `desktop_thumb` and real
`export_saved_chat` requested an allocation of **5,184,000,000 bytes** before
producing a `320 x 213` thumbnail. The request came from expanding packed samples
into `serde_json::Value`; the path also created a vector object per source pixel
before scaling. A compressed-byte limit did not bound decoded working memory.

Both unchanged-production tests aborted in child processes with a **512 MiB
address-space cap**. The number above is the allocation request printed by Rust,
not measured peak RSS or a claim that the host allocated 5 GB. Parent-owned
temporary directories and disabled core dumps contained the failure. Default
Rust allocation failure can abort without unwinding, so `catch_unwind` alone is
not a reliable repair for this path.

### Implemented repair and acceptance

The internal ICC path now returns packed byte buffers. Its public JSON parity
wrapper retains the same output. A private flat scaler reuses the existing tap
weights, all four up/down axis orders, shifts, and final byte truncation, with a
contiguous intermediate at the first scaled dimensions. Grayscale expands during
sampling instead of creating a full RGB object graph. The JPEG path calls these
internal helpers directly; public APIs and existing format limits are unchanged.

`tests/parity_thumbnail_resources.rs` retains both original 24 MP cases, with
512 MiB address-space and 120-second CPU limits applied before the child starts.
It requires an actual correctly sized/colored JPEG. The archive case also checks
source copying, thumbnail links, HTML/JSON reports, and staging cleanup. Dropping
the thumbnail, shrinking the fixture, or merely refusing ordinary photos would
not pass. These resource assertions run on Linux; cross-platform golden tests
remain enabled elsewhere.

A 36-combination RGB/grayscale cross-check compares the new flat path with the
unchanged public scaler. Existing pinned Qt/ICC/JPEG byte-exact goldens cover
rendering compatibility. Their provenance is retained in
[`tests/fixtures/tdexport_icc`](../../tests/fixtures/tdexport_icc/README.md).
The 512 MiB result is specific to the tested 24 MP cases, not a universal memory
promise for every accepted 100 MP image or arbitrary caller-supplied target size.

Sources: [ICC buffers](../../src/ported/tdexport_qt_icc.rs),
[JPEG thumbnail path](../../src/ported/tdexport_qt_jpeg.rs),
[flat scaler and parity test](../../src/ported/tdexport_qt_scale.rs), and
[capped resource regressions](../../tests/parity_thumbnail_resources.rs).

## Concurrent main update and integration

After the original repair's CI passed, the owner published
[`de46b6c4ca1c13336f9e5c1b21fdb30ea7771562`](https://github.com/KiaroSama/Grammers-Secret-Chat/commit/de46b6c4ca1c13336f9e5c1b21fdb30ea7771562).
PR #53 was rebased onto that exact main commit. The sole text conflict was in
`docs/integration-boundaries.md`; its resolution preserves both the owner's new
feature contracts and the complete TTL/retry/event ownership contracts above.
No production-code conflict required a manual resolution.

A bounded interaction review confirmed that typed snapshots still convert
through the existing persisted protocol representation, including TTL, counters,
and held keys; manager outbox identities remain separate. The richer exporter
still uses the repaired thumbnail path and stages its sidecars before publishing.
Caller-owned orchestration neither changes text-send locking nor drains manager
events. `AutoSaveSubscription::on_message` is a caller-fed recorder, not an
automatic event subscription.

The owner's property tests, typed-state and binding-migration tests, checkpoint
measurement harness, orchestration tests, and documentation are preserved. The
combined-tree acceptance result and exact published-head CI are recorded on
[PR #53](https://github.com/KiaroSama/Grammers-Secret-Chat/pull/53); the earlier
318-test results and original red reproductions above retain their original
provenance and must not be represented as the new head's result.

The added opt-in interoperability workflow currently checks secret availability
and executes offline transport tests. It does not execute a live-account harness.
Any future authorized live validation should extend that workflow and report
live evidence separately, rather than adding a duplicate workflow or treating
credential presence as a completed live exchange.
