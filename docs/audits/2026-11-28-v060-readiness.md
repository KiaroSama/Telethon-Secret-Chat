## R01 — Durable input can remain idle after its chat becomes ready

**Impact:** delivery can stall even though the ciphertext is durably retained and
the chat has become usable. A later external drain or update can recover it,
but that external event is not guaranteed. The reproduced failure is a liveness
defect, not demonstrated ciphertext loss or a cryptographic break.

At the baseline, `StrongSecretChatManager::replay` visits each batch once. It
skips a message for a `Requested`, `Waiting`, or paused chat. A subsequent batch
may establish that chat, but the earlier row is not revisited. `start()` also
performs only that one drain. Public `accept` and `create` delegate to the base
manager without waking the ingress journal. Acceptance can commit a `Ready`
state before its initial layer notification fails or the caller cancels, so an
`Ok`-only wake would leave the error and cancellation variants unresolved.
The same boundary exists in `resume_chat`: custody is durably unpaused before
the method awaits retained-send retries, but the Strong wrapper's trailing drain
was reached only on success. Resume errors and cancellation can therefore leave
eligible input idle too.

`new_encrypted_messages`. That ordering cannot repair an earlier, separately
committed journal batch.

The tests exercise real encrypted custody, real frame encryption/decryption,
SDK ingress receipt capture, durable cursor application, and consumer receipts.
Only external RPC behavior is supplied by the deterministic test transport.
They verify stable body/sequence identity across another drain and reconstruction,
then consumer acknowledgement and restart without redelivery.

### Repair and invariants

1. A replay pass reports actual row application or retirement. Its existing
   owned replay job takes another snapshot after progress or an explicit wake.
   It stops when neither occurs. The entire job retains its original finite
   `operation_seconds` deadline. New capture alone is not counted as application
   progress, and blocked rows cannot create an unbounded polling loop.
2. `accept`, `create`, and `resume_chat` arm a borrowed readiness guard before
   polling the base operation. Normal success, normal error, and future destruction
   all enqueue replay. Inner operation/creation resources are destroyed before cancellation
   queues its wake, so creation admission and outbound locks cannot be left
   artificially active when replay decides whether a row is ready or terminal.
3. The guard captures the Tokio runtime handle when armed. Cancellation may drop
   the future outside an entered runtime; queueing does not require a fresh
   ambient runtime lookup. The live runtime must still be driven. Process or
   runtime shutdown is recovered through the already durable startup journal.
4. Reentrant same-manager operations enqueue without joining their own caller.
   Top-level normal completion can join the finite replay. A failed establishment
   keeps its original error; a replay error does not replace that error.
5. Replay admission rechecks manager readiness while holding the replay slot
   lock. All work stays in the existing owned task slot, so shutdown fences
   admission and cancels/joins that work. User callback admission is not used as
   the correctness mechanism, and no detached watcher is introduced.

The private row-status query reads the committed cursor/applied set under the
coordinator lock; it does not clone entire pending ledgers to infer progress.
Terminal retirement still uses the existing atomic storage transaction. A
storage refusal remains an error. Waiting, paused, and uncertain creation rows
remain protected, including across restart. The public API and durable schema
remain unchanged.

Three adjacent controls cover the new guard's distinct ownership boundaries:
completed creation releases an otherwise absent held row, cancellation before
the DH result releases creation admission before replay, and cancellation outside
an entered Tokio runtime still queues onto the captured live runtime. These are
additional repair controls, not separate findings or claimed results of the
eight-case historical proof run. Two resume regressions additionally require
delivery after a failed or cancelled retained-send retry, while preserving its
exact error and pending ciphertext identity.

## Verification and completion gate

Keep every existing test identity and platform exclusion. Add the readiness
cases to `migration/current-rust-cases.json` (2271 total); the normal seven-leg Rust workflow
must verify actual execution against that inventory. The temporary proof-only
workflow is removed from the repaired tree. Formatting, Clippy, all first-party
targets, vendor tests, scanner tests, source-package/installed-consumer checks,
CodeQL, and Gitleaks remain enabled on the final PR head. A historical green
main/tag run or the intentionally red checkpoint is not final-head acceptance.

The audit environment's local prerequisite compilation was killed by `SIGKILL`
before it executed any tests. That is an environment limitation, not the RED
result above. The successful remote compilation and five observed failures are
the reproduction evidence. Live Telegram cases remain explicitly ignored unless
run separately with the owner's authorized accounts. Offline fixtures do not
claim official-client interoperability.

The current tag badge already derives its version from repository tags, and
Dependabot already checks Cargo and GitHub Actions daily. No pin or schedule
change is justified by R01. The existing v0.6.0 tag workflow signed and published
its four platform archives; the repair branch is not itself a signed release.

## Primary references and decisions

- [Telegram update ordering](https://core.telegram.org/api/updates): retain exact
  durable sequence and duplicate-handling obligations when revisiting rows.
- [Telegram secret chats](https://core.telegram.org/api/end-to-end): preserve
  handshake state and encrypted-message custody; do not alter protocol semantics
  to conceal an application scheduling defect.
- [Tokio runtime handle](https://docs.rs/tokio/1.54.1/tokio/runtime/struct.Handle.html):
  capture the handle before cancellation can leave the runtime context.
- [Tokio task ownership](https://docs.rs/tokio/1.54.1/tokio/task/struct.JoinHandle.html):
  retain replay handles for cancellation and joining instead of detaching work.
- [Pinned SDK message-box ordering](../../vendor/grammers/grammers-session/src/message_box/mod.rs)
  and [qts classification](../../vendor/grammers/grammers-session/src/message_box/adaptor.rs)
  are reviewed from the actual vendored source, rather than assuming envelope
  order is the replay order.
- [GitHub Spec Kit](https://github.com/github/spec-kit): the owner's configured
  review chain governs the subsequent review/integration session; this document
  does not claim execution of private Rules or hooks absent from this checkout.
