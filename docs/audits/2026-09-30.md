## Findings, corrections and closure tests

### F01 — High: short ciphertext read publishes partial plaintext

`files.save` measured a stream before decoding, but the stream could subsequently yield fewer block-aligned bytes. Without final consumption validation, the decoder ended normally and the temporary file replaced an existing destination with partial plaintext.

Implemented: exact nonnegative integer size validation and actual consumed-byte accounting in `decrypt_stream`, with final length/padding relationship validation before `save` replaces the destination. Failure cleans its temporary file and preserves the destination. Regression: `test_short_ciphertext_read_does_not_replace_the_destination` in `test_reaudit_stream_lifecycle.py` uses a stream whose reported/readable lengths disagree. Existing chunked IGE, padding and key tests remain. Close only when premature EOF and malformed lengths never publish partial files. This does not add a payload authentication tag; the file-key fingerprint is not full ciphertext authentication.

### F02 — High: temporary cleanup deletes live writes

File saves and store startup deleted every matching temporary prefix, including another active writer. A matching filename is not evidence of a crash. Tests reproduce concurrent saves and a second store opening while the first is committing.

Implemented: `temporary.py` uses PID-tagged names, a shared reentrant lock and an active-path registry spanning creation through replacement/cleanup. Other live or unqueryable owners are preserved. Only identifiable inactive leftovers are reaped; legacy names and symlinks are retained for explicit offline maintenance. Windows uses a SYNCHRONIZE process handle and `WaitForSingleObject(..., 0)`, never `os.kill(pid, 0)` as a Windows liveness probe. POSIX permission/range/unknown failures are conservative. Existing POSIX store permissions are restricted before reading. Logs expose types, not file/key data.

Regressions: two saves, concurrent store open, real subprocess alive/then exited, registry lifetime, legacy/unknown/unrelated names, unqueryable/out-of-range owners and redacted errors in `test_temporary_ownership.py` and the stream/lifecycle suite. Existing stale-name fixtures now represent identifiable inactive owners; separate tests preserve the legacy rule. Close only with Windows execution and proof no active writer is removed. This does not permit concurrent independent writers to the same FileStorage: the single-writer contract remains. Legacy plaintext leftovers require offline cleanup AFTER all writers stop, as README/architecture now state.

### F03 — High: pre-restart uploads overwrite current state or block new sends

Uploading outside the chat lock is intentional, but the upload retained the old chat object. Stop/start restored a new object; the old upload could later persist stale counters. Keeping the old outbound lock also blocked new-run sends until old I/O returned.

Implemented: lifecycle generations, generation checks around outbound reservations, and current-chat identity checks at send/transaction boundaries. Stale work raises `ManagerStopping` rather than saving/reserving. Startup creates fresh outbound locks; old tasks retain old locks and fail their epoch checks. Old-lifecycle create results are discarded rather than installed.

Regressions: `test_upload_from_a_previous_run_cannot_overwrite_restarted_state` advances the restarted receive state and compares stored records; `test_new_run_does_not_wait_for_an_old_upload` requires a new send to proceed before releasing old I/O. Preserve normal same-lifecycle ordering. Rejection cannot undo ciphertext already uploaded to Telegram; do not claim all external I/O was cancelled.

### F04 — High: discard arriving before create's RPC response is lost

The early update cache handled ready messages, not an early discard. Returning a waiting response after the discard could create a requested-looking chat again.

Implemented: bounded early discard buffering during active creation, with terminal precedence over ready/waiting responses; normal close handling scrubs handshake state. Regression: `test_early_discard_during_create_is_terminal` emits discard inside the RPC before returning waiting and requires CLOSED. Close only when terminal precedence remains through duplicate/early updates, without unbounded cache growth or interference with unrelated established chats.

### F05 — High: malformed persisted runtime fields survive restoration

Additional control fields were trusted after only partial validation, including string Booleans, Boolean/negative TTLs, malformed hash types, invalid/nonfinite timestamps and collection shapes. Failures could appear after installation at an unrelated operation.

Implemented: exact types, bounds, finite timestamps, byte/key/hash shapes, handshake structures, DH integer shape/range, recognized exchange roles and required collection/range checks in `chat._validate`; redacted `StoreCorrupt` before installation. Compatible defaults remain. Individual corrupt mailbox entries preserve the existing isolate/drop-and-report policy, rather than blocking every subsequent message.

Regression: 14-case `test_corrupt_runtime_fields_fail_at_the_restore_boundary`, existing startup/storage tests. Close only when no partially installed manager or secret-bearing raw error escapes. This validates structure and the enforced invariants; it is not a proof of every possible semantic property of an externally forged store.

### F06 — High: forwarding bypasses key validation and caption policy

Saving checked media key/IV against the attached file fingerprint; forwarding did not. Forwarding could reserve an unusable reference. It also bypassed the caption rejection for stickers and round videos.

Implemented: shared `_file_of` validation of key/IV lengths, size and fingerprint for both message and `MediaReference` inputs BEFORE reservation/RPC; captionless-attribute detection in forwarding. Regressions cover both damaged input representations with unchanged storage/no RPC, and both captionless kinds. Valid forwarding continues to reuse the original key/server handle without download/upload. Its privacy consequence is intentional: holders of the original key can read the forwarded copy. Fresh encryption requires a new upload.

### F07 — Medium: restored media references admit invalid/trailing data

`MediaReference.from_dict` accepted Boolean versions, negative size, trailing TL bytes and inconsistent fingerprints. Serialization alone is not validation.

Implemented: decode one complete file-media result family, validate usable keys/size, exact supported integer version and fingerprint join; revalidate at runtime boundaries, including direct dataclass instances. Regression cases cover each malformed form plus valid round-trip. Invalid references must fail before network/destination effects, with generic errors rather than encoded keys/media in diagnostics.

### F08 — High: TL parser accepts known constructors in wrong result families

Recognizing a constructor ID does not make it valid in a slot declared as media, entity, action, attribute or sticker-set. The generated reader did not enforce those nested/vector result families consistently.

Implemented in `tools/generate_schema.py`: generated reads pass expected result families; `read_object(expected=...)` rejects mismatches before field parsing. All 90 constructors regenerated. Regression tests substitute known wrong-family constructors in five field categories. A separate depth-limit test retains nesting protection; valid constructor round trips stay enabled. No hand-edit-only generated correction is acceptable. Require non-mutating generation `--check`, identical valid serialization, bounded malformed collections and fatal framing rejection under the existing authenticated-malformed-message policy.

### F09 — High: service-action persistence failure leaves RAM changed

Received TTL/layer effects could mutate the live chat before durable delivery completed. A failed write left RAM and storage inconsistent with the retained mailbox.

Implemented: apply effects inside the existing `_atomic` checkpoint; publish service events only after commitment. Regression injects a write failure and requires RAM TTL and stored TTL both zero, the pending delivery retained, and no service event. The private test harness supplies a real manager for the transaction boundary. Preserve retry behavior, monotonic layer handling and the existing distinction between capability layer and wrapper layer.

### F10 — Medium: shutdown cancellation and handler ownership are inconsistent

Concurrent or handler-initiated stop callers could interfere, one cancelled caller could disrupt shared completion, returned Futures during stopping could be abandoned, and a failure after caller cancellation could become unretrieved.

Implemented: one shared stop coordinator, cancellation-isolated caller waits, explicit
participating/draining-handler ownership, startup waiting for completion, and redacted
retrieval of shutdown and discarded-handler failures. Normal waiting callers still receive
the original failure. **The first implementation was insufficient on Python 3.14; it is not
accepted merely because Python 3.13 passed.** The final correction is:

- `manager._wait_stopped` awaits `asyncio.wait((task,))`, then retrieves `task.result()`.
  Unlike an exceptional shield proxy, this wait cannot emit the original exception after its
  caller cancels. The coordinator's done callback still retrieves and logs its type only.
  Both `start` and `stop` use this boundary.
- `dispatch._cancel_handler_tasks` records the exact tasks being drained. A handler's
  cancellation cleanup can request the already-owned stop without awaiting its own
  coordinator. Restart from that cleanup raises `ManagerStopping` instead of making a cycle.
- A failed shutdown leaves work to retry; `start` completes that shutdown before reinstalling
  the subscription. It cannot simply return because `_running` was left true after a save error.
- Discarded Futures/Tasks are held until completion, cancelled, and observed with safe
  handler-name-only diagnostics. A Task that raises during cancellation cannot escape to
  asyncio's raw exception logger, including cancellation before its wrapper starts.

`tests/unit/test_shutdown_convergence.py` permanently exercises the nine combinations:
cleanup requesting start/stop; restart after a failed save; cancellation of start/stop waiters
while another observes the original failure; and done Futures/cancelled Tasks returned
while stopping or before wrapper execution. Existing cancellation redaction, concurrent stop,
async-handler isolation and RuntimeWarning-as-error tests remain. The tests bound their waits
and release failed implementations so a regression does not become another hung CI run.

The follow-through also checks handlers returning an existing `asyncio.Task`, not just
coroutines. The first correction still deadlocked in both start/stop cleanup cases because
only the wrapper was marked as draining. Both failures were reproduced with bounded tests
before correction. A wrapper-to-Future dependency map now marks the directly awaited Task
as part of the same drain and excludes wrappers whose returned Task is itself a legitimate
stop caller. It cancels the wrapper once, not both sides of the same await. Discarded Tasks
are marked during their cancellation cleanup so they cannot restart a stopping manager.
The mapping and drain markers are removed on completion. Permanent regressions include
both returned-Task cleanup cases, a returned Task initiating stop normally, and restart
rejection from a discarded Task. This is F10 completion, not a deferred follow-up item.

**Closure is strict:** final Python 3.14 must pass without logger filters, warning suppression,
exception-text changes to test fixtures, skipped assertions, or altered error expectations.
Other live waiters must still see the original exception. Handler code that refuses to
finish despite cancellation remains application-owned; this is not a guarantee of bounded
shutdown for arbitrary uncooperative third-party coroutines.
