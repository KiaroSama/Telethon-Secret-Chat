## Confirmed findings and implemented remedies

### F01 — High: concurrent and uncertain sends could reuse a sequence position

**Affected:** `src/manager.rs`; `tests/manager_audit.rs`; `tests/lifecycle_contract.rs`.

The manager released state before awaiting transport and advanced its outgoing counter only after successful completion. Parallel sends could construct the same sequence number. A network error after server acceptance, or cancellation while awaiting the RPC, allowed a later call to reuse that position. Re-encryption also changed random padding and ciphertext for a logically identical retry.

The fix serializes outbound RPCs per chat, retains the exact encrypted frame and identity, and reserves the sequence before the first network await. A retry with the same retained `random_id` and identical content uses the same bytes. Reusing that identifier for changed content refuses. Other chats and inbound handling remain able to progress. Records stay retained until authenticated peer acknowledgement, with finite count/byte budgets and no silent eviction.

**Closure tests:** concurrent manual polling; simulated acceptance followed by transport error; cancellation during the RPC; exact byte-for-byte retry; conflicting retry identity; independent chat progress; capacity release only after peer acknowledgement; shutdown while another sender is queued. The old test that required rolling the counter back after a transport failure was corrected because that behavior was unsafe.

### F02 — High: gaps were lost, recovered messages were dropped, and Resend was not connected to transport

**Affected:** `src/protocol.rs`, `src/ported/sequence.rs`, `src/manager.rs`; both manager audit suites and `tests/protocol_audit.rs`.

The receive path did not preserve all required gap state and its single-result interface could discard additional messages released when a gap closed. Detecting a gap did not actually send the required recovery service. Authenticated peer Resend actions were not answered through the runtime outbox.

The core now retains bounded pending frames and exposes a batch result. `receive_frames` publishes every released message in order. The compatibility core API exposes extra messages through `take_ready_messages`; the manager's batch API should be preferred. A newly discovered gap creates one retained Resend service, and a duplicate frame does not create another. Incoming Resend actions are handled immediately, including while their own sequence is behind a gap, and before acknowledgement pruning. Requested ranges are checked for parity, order, length, and complete retention. Recovery transmits the original ciphertext. An unsatisfiable authenticated range closes the chat instead of silently continuing.

Outbox transmission revisions prevent a Resend received during an in-flight RPC from being overwritten by that RPC's later completion. Acknowledged records requested for replay remain until the replay settles. Successful outbound finalization releases its ordering lock while still holding the state lock around the last empty-queue check; otherwise a concurrent receiver could enqueue a response after the driver had finished checking. Authenticated acknowledgement also settles a send whose RPC subsequently returns an error, preventing a false retry request. Outgoing recovery and rekey state are staged on a cloned core, with capacity checked before state/event publication, so a refusal does not consume a sequence or lose a needed response.

**Closure tests:** deliver message 3 before 1 and 2; recover all 3 exactly once; duplicate gaps; immediate Resend bypass; missing retained position; wrong range/parity; response capacity exhaustion followed by successful retry; correct service-RPC routing; exact replay bytes.

### F03 — High: the native runtime lacked a complete operational rekey lifecycle

**Affected:** `src/ported/rekey.rs`, `src/protocol.rs`, `src/manager.rs`.

The old synthetic rekey adapter represented decisions without providing an operational RequestKey/AcceptKey/CommitKey/Noop exchange in the manager. A migration unit count did not establish forward-secret key rotation.

The runtime now retains original validated DH parameters, exchange identity/role, secret/pending/previous key slots, message counts, and key age. Commit ciphertext is prepared under the old key before adoption. Confirmation uses the new key. Authenticated pending-key traffic handles a lost Commit, while the previous key remains available until confirmation and gap recovery permit retirement. Collision ordering, equal exchange IDs, matching/unrelated Abort, malformed peer values, and fingerprint mismatch have explicit behavior. A missing original DH configuration fails closed when rekey is required.

The manager implements `configure_chat_dh`, `start_rekey`, conversation `send_service_action`, and a distinct `SecretTransport::send_encrypted_service` hook. The default service hook explicitly refuses; real adapters must use Telegram's service RPC. Automatic rotation is evaluated on sends **and receives**, including the transaction that crosses the `>100` combined-message threshold, provided there has been outgoing traffic. The age threshold is also checked on activity. No background timer wakes an entirely idle manager.

**Closure tests:** real four-service two-peer exchange; text under the new key; old-key Commit encoding; lost Commit with pending-key traffic and old-frame recovery; signed collision cases; malformed/tampered peer values; abort cleanup; no direct active-key overwrite; sequence exhaustion; exact retry of failed service delivery; capacity refusal without a phantom exchange; receive-driven automatic rotation.

### F04 — High: lifecycle/key validation allowed unsafe state changes and unnecessary secret copies

**Affected:** `src/protocol.rs`, `src/ported/handshake.rs`, `src/ported/crypto.rs`.

Duplicate registration could replace a live chat. Key adoption could revive closed state or replace an established key outside the rekey state machine. Zero DH exponents could produce a publicly predictable result. Public crypto helpers accepted incorrect key/message-key lengths. Native wrappers copied key material through adapter JSON arrays and arbitrary-precision representations.

Registration now rejects both live identities and tombstones; closed chats cannot be revived; active replacement is owned by rekey. DH exponents must be positive and bounded. Runtime 2048-bit exponentiation uses fixed-precision `crypto-bigint` values with zeroizing owned exponent/result buffers. Native crypto paths borrow keys, validate lengths, use constant-time fingerprint/message-key comparisons, and zeroize owned key/decrypted intermediates. This improves control of owned buffers; it is not a claim that a compiler or operating system can erase every historical stack/register copy.

**Closure tests:** duplicate registration before/after closure; direct active replacement; zero exponent; malformed key lengths; real 2048-bit DH agreement and composite-prime refusal; tampered fingerprint without key adoption; secret-free debug output.

### F05 — High/Medium: authenticated wire validation and TL encoding were inconsistent

**Affected:** `src/ported/crypto.rs`, `src/ported/schema_secret_tl.rs`, `src/ported/sequence.rs`, `src/protocol.rs`.

Checks were missing or inconsistent for the upper padding bound, four-byte TL alignment, reserved string-length marker, noncanonical extended short lengths, zero string padding, nested result families/depth, and trailing uninterpreted bytes. The wrapper lost `silent` and `no_webpage`. Capability announcement and actual wrapper layer were conflated, rejecting a legitimate ordered older wrapper after NotifyLayer.

Crypto enforces authenticated body alignment and padding `12..=1024`; TL parsing/encoding enforce matching canonical constraints and depth bounds. The wrapper's `random_bytes` must contain at least `15` bytes; a shorter wrapper is ignored without closing/advancing the chat. Flags survive the wrapper. Advertised capability and observed wrapper layer are distinct. Authenticated fatal schema/sequence violations close state; unauthenticated bad ciphertext is rejected without letting arbitrary traffic close a healthy chat. A TDLib ciphertext bucket size must not be mistaken for the padding size; the protocol-reference note was corrected.

**Closure tests:** real encrypted malformed packets for excessive padding/alignment; wrong parity; authenticated invalid inner object; string markers and padding; wrong constructor result family; encoder/decoder nesting; negative initial depth; trailing bytes; flag round trip; NotifyLayer followed by an otherwise valid older wrapper.

### F06 — Medium: count-only recovery limits allowed excessive retained memory

**Affected:** `src/protocol.rs`, `src/manager.rs`, `src/ported/rekey.rs`.

A `1000`-position gap limit alone did not bound bytes retained by large valid frames. Text/service preparation also needed to respect the receive implementation's frame ceiling.

The implementation has explicit resource limits: at most `1 MiB` per encrypted frame and `16 MiB` aggregate buffered gap body bytes, in addition to the sequence window. These are local implementation limits, not claimed Telegram protocol constants. Oversized raw input refuses before decryption/allocation and leaves the chat usable; exhausting the authenticated recovery obligation budget closes it. Oversized outgoing text or service preparation refuses before consuming sequence state. Outbox defaults are `1024` records and `16 MiB` per chat.

**Closure tests:** oversized raw frame; genuinely encrypted large pending frames exceeding the aggregate; oversized outgoing text and service with unchanged sequence. Registered chat IDs and queued application events remain caller-owned lifetime collections; applications must bound manager ownership and drain events. See the optional bounded-event design below rather than silently dropping events.

### F07 — High: encrypted stores could destroy the committed file before replacement

**Affected:** `src/storage_file.rs`, `src/custody.rs`, `src/ingress.rs`.

Both stores removed the destination before renaming a replacement, creating a data-loss window. File/directory durability claims exceeded the operations performed.

The shared replacement helper writes an exclusively created sibling staging file, flushes the file, replaces the destination without pre-unlinking it, and flushes the parent directory on Unix. It distinguishes failure before replacement from failure after replacement. An uncertain post-replacement failure poisons the open state until reopening; it does not allow a stale in-memory controller to continue writing as if nothing happened. Windows parent-directory durability is not claimed to be identical to Unix.

**Closure tests:** replacement failure preserves the previous committed payload; post-replacement uncertainty refuses continued operations; authenticated reopen; unit fault injection at the replacement boundary. These tests cover operation failures, not a physical power-cut experiment.

### F08 — High: fixed temporary paths could clobber or delete unrelated files

**Affected:** shared storage helper and both stores.

Predictable `.tmp` names could overwrite an existing unrelated file, follow a staging symlink, or be deleted without ownership proof. Existing targets and cleanup also lacked consistent file/path/authentication checks.

Staging now uses a unique random/PID suffix with `create_new`, Unix `0600`, and an ownership guard that only removes a staging path it actually created. Storage requires an absolute path, canonical parent, and regular non-symlink file. Reads are bounded at `64 MiB`. Cleanup authenticates the owned store before deletion and preserves unrelated `.tmp` files and symlinks. A persistent sidecar lock coordinates cooperating writers and is not deleted to manufacture a new lock inode.

**Closure tests:** unrelated staging sentinel survives save/cleanup; staging symlink target remains unchanged; relative-path refusal; owner-only Unix mode; unauthenticated cleanup refusal; lock contention. Directory protection against a hostile operating-system user remains an environmental requirement.

### F09 — High: stale or fresh writers could overwrite committed custody

**Affected:** custody save/restore and ingress snapshot persistence.

A newly created controller could overwrite an existing ingress file, and two restored controllers could overwrite each other's newer snapshots. Custody saves could replace records owned by another authorization.

Read-modify-write and revision comparison now happen under the store lock. Existing ingress files require `restore`; stale revision updates refuse. Custody verifies consistent authorization over the entire stored document and preserves existing owner records. Failed writes do not publish candidate in-memory state.

**Closure tests:** fresh controller against an existing file; two restored writers where the second becomes stale; cross-authorization replacement; contention; authenticated state/accounting validation. Authenticated encryption and revision checks do not themselves prevent an attacker from replacing the entire file with an older authentic snapshot; external anti-rollback storage would be a separate capability.

### F10 — High: drain reported success after losing pending obligations on disk failure

**Affected:** `DurableIngressController::drain_in_order`, `pending_in_order`, `acknowledge`.

The original drain removed pending records in memory, ignored persistence failure, and returned apparent success. That made both data loss and duplicate restart processing possible.

`drain_in_order` now returns `Result`, persists a candidate snapshot before adopting it, and retains obligations on failure. Non-consuming `pending_in_order` plus explicit durable `acknowledge(stream, order)` support application processing followed by settlement. Exact duplicate acknowledgement is idempotent; unknown identity refuses. Callers must update for the changed fallible signature.

**Closure tests:** drain failure retains pending records; failed acknowledgement retains the obligation; poll does not consume; restart after persisted acknowledgement; duplicate and unknown acknowledgement. The batch drain still settles before the consumer performs external work, so crash-sensitive consumers should use poll-plus-ack.

### F11 — High: bounded custody silently evicted data and persisted volatile modes

**Affected:** `CustodyRecord`, encrypted custody persistence.

Limit exhaustion evicted outstanding payloads, converting a finite budget into silent loss. Records marked transient or memory-only could cross the disk persistence boundary.

Exhaustion now refuses and pauses while preserving every retained payload. Disk persistence refuses volatile modes, validates the complete restored document, and checks accounting, status, limits, and owner consistency. The old test that asserted eviction was replaced with preservation assertions. `resume` clears a local flag only; the application must establish protocol continuity before resuming real work.

**Closure tests:** count and byte exhaustion preserve all prior data; accounting mismatch; invalid status/limits; transient/memory-only persistence refusal; cross-owner records.

### F12 — Medium: ingress duplicate ordering, validation, and finite-history handling were unsafe

**Affected:** `src/ingress.rs`; `tests/storage_audit.rs`.

An exact retry could be rejected at a full queue because capacity was checked before deduplication. Conflicting pending identities could be treated as harmless duplicates. Restored authenticated documents trusted inconsistent fields and could exceed tightened limits.

Exact duplicate detection precedes new-record capacity checks, while conflicting payload/chat identities refuse. Restoration validates schema, order identities, verification status, seen membership, aggregate accounting, and configured limits. Hard ceilings are `4096` pending records, `1 MiB` payload, `16 MiB` aggregate pending payload, `4096` streams, and `65536` deduplication identities. Exhaustion refuses; history is never silently evicted. This bounded container does not claim an eternal deduplication history.

**Closure tests:** exact full-queue retry; conflicting duplicate; zero limits/empty owner; malformed authenticated state; restore above configured limits; finite history/stream accounting.

### F13 — Medium: diagnostic output could disclose payloads or adapter credentials

**Affected:** accepted messages, custody/ingress records, manager transport error boundary.

Derived `Debug` printed plaintext, raw body/payload bytes, owner/stream text, or action values. `close_chat` returned an untrusted adapter error verbatim even though send errors were sanitized.

Custom debug summaries expose only structural metadata and lengths. The manager maps send/discard adapter failures to fixed safe diagnostics. The close/shutdown state check is repeated after acquiring the state lock. Empty/whitespace authorization identity is rejected. Application-supplied reasons remain application data; do not put credentials in them or log payloads yourself.

**Closure tests:** credential/plaintext sentinel absence in debug/display paths; retained useful lengths; failed remote discard after local closure; queued work after shutdown. `shutdown` stops new work and clears local state but does not join caller-owned RPC futures already in progress.

### F14 — Medium: exported JSON strings were invalid or Unicode-corrupt

**Affected:** `src/ported/tdexport_json_serialize.rs`; `tests/export_audit.rs`.

Control characters were emitted as `\\xNN`, which JSON does not permit. Escaping U+2028/U+2029 also appended stray UTF-8 continuation bytes. A legacy fixture expected the malformed output and therefore concealed the defect.

Controls now use valid `\\u00NN` escapes, separators round-trip correctly, and invalid UTF-8 bytes are rejected rather than silently emitted as text. The misleading fixture was corrected against JSON syntax.

**Closure tests:** all control characters `0..31`, line/paragraph separators, Persian, Japanese, emoji, valid JSON parsing and exact round trip, invalid UTF-8 refusal, and existing golden export fixtures. This fixes the serializer; it does not create a full native archive writer.

### F15 — Medium: public compatibility constants did not match their advertised baseline

**Affected:** `src/public_api.rs`; `tests/public_api_audit.rs`.

The media vocabulary used the wrong voice label and omitted baseline kinds; captionless media membership was wrong; the fourth key-identicon palette color differed from the reference.

The eight supported metadata kinds, `voice_note`, captionless `sticker`/`video_note`, and palette color `(47, 153, 201)` / `#2F99C9` are restored. Tests check both the exported values and actual rendered palette use. These constants do not imply a complete upload/download/forwarding API.

### F16 — Medium: maintenance commands could falsely pass bad inputs or overwrite fixed temporary outputs

**Affected:** both native command binaries and their `ported/tool_*` helpers; `tests/maintenance_commands.rs`.

The test-matrix checker silently ignored unreadable/malformed extra artifacts, suite-level failures, and missing test identities. CLI help/unknown-argument behavior was inconsistent. Schema parsing accepted malformed or duplicate constructors. Fixed temporary paths risked clobbering unrelated files.

Inputs now fail closed with meaningful exit status; suite failures and blank identities are validated; malformed/duplicate constructor definitions refuse. The generators use owned atomic staging. Commands expose timestamped `INFO`, `WARNING`, `ERROR`, and `DEBUG` diagnostics without printing secret inputs.

**Closure tests:** actual built command invocation for malformed/missing artifacts, suite failure, invalid testcase identity, help/unknown options, bad/duplicate schema, and staging sentinels. Generated schema is validated from the source-distribution installation as well.

### F17 — High/Medium: CI and packaging did not test important shipped behavior

**Affected:** `.github/workflows`, `.github/scripts`, Cargo workspace/lock, `tools/secret-scan`, Dependabot.

Archiving files did not prove the extracted package compiled or worked as a Git dependency. Vendored transport crate tests were outside the root test invocation. The generator needed a schema that release archives could omit. Protected signing could prevent ordinary main-push workflow completion from clearly representing validation. There was no stable required aggregate for all primary validation jobs.

Standalone scanner safety tests run with formatting and strict linting. Root default members keep ordinary first-party runs intentional; first-party Clippy uses `--no-deps` so pinned vendor style warnings are not misrepresented as application defects.

The workflow runs on push, pull request, merge group, and explicit dispatch. A stable `Rust CI` aggregate reports the validation outcome. Protected release signing is limited to version tags or an explicit main dispatch. Dependencies remain pinned; the workspace lock gains vendor optional/dev dependencies without opportunistically upgrading existing identities. Dependabot covers the root workspace, standalone scanner, and pinned GitHub Actions. The owner's concurrent Gitleaks all-push change is preserved.

**Closure tests:** native matrix and vendor jobs on final head; extracted archive compilation; exact-revision downstream consumer; actual Git installation with explicit `kiaro-secret-chat` package selection; all workflow files parsed by actionlint; PowerShell scripts parsed/run under PowerShell 7; scanner refusal paths. Required-check settings are repository policy and must be verified by the merge agent, not inferred from YAML alone.

## Optional improvements for owner/agent evaluation

These are design proposals, not hidden claims of implemented functionality:

* **Typed public messages/actions:** replace general `serde_json::Value` at native API boundaries with enums/validated structs while retaining legacy adapter fixtures. This would make invalid action families unrepresentable and document TTL/read/delete responsibilities more clearly.
* **An integrated durable manager:** specify one transaction boundary spanning chat counters, active/pending/previous keys, retained outbox, applied ingress cursor, and emitted delivery IDs. Prove crash/restart behavior before attaching transport acknowledgements. A persisted ciphertext queue alone is not that transaction.
* **Bounded event/chat ownership:** add configurable global chat/event/byte budgets and an acknowledgement-aware event consumer. Reserve event capacity before accepting protocol effects; never drop a required event or close notification silently. Decide how tombstones can be retired safely.
* **A real opt-in interoperability harness:** two explicitly authorized disposable Telegram accounts, pinned desktop/Android or independent implementation, negotiation, text/services, rekey, gaps, account reconnect, and media cases. Gate it separately from offline CI and report unavailable credentials as unavailable. Never commit sessions or log API credentials.
* **Property/fuzz testing:** bounded fuzz targets for TL decoder/encoder round trips, frame parsing, and authenticated snapshot validation; deterministic seeds and regression corpora for found failures. Add only meaningful gates, with runtime limits and artifact redaction.
* **Restore historical high-level features only from an accepted specification:** native media transfer, autosave/archive orchestration, durable ingress integration, and establishment transport should each have compiled consumer examples and realistic end-to-end acceptance. Avoid placeholder aliases that make an inventory look complete.

GPU acceleration is not proposed for this small per-message crypto path: it would add dependencies and transfer overhead without measured evidence of benefit. Profile real workloads before introducing a new backend.
