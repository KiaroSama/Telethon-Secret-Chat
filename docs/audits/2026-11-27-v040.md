## Confirmed failure families and implemented repairs

### A01 — Authorization binding used the wrong identity and missed local key replacement

**Impact:** high; an unusable current-session check and incorrect ownership continuity.

The actual adapter rejected a typed current authorization with management hash `0`, and its previous binding relied on the session-management hash rather than the actual local permanent authorization key. A real `grammers::Client` backed by a synthetic memory session entered the RPC path after its local key was replaced. Telegram Desktop also normalizes its current session's management identifier to zero; that management value is not sufficient proof of key identity. This observation is not a live capture of Telegram's response.

The small vendored `Client::authorization_key_tag()` API returns the home DC and an opaque tag using the existing tag implementation. It exposes no raw key. `GrammersTransport` now combines that tag with the remotely verified user, DC, and caller generation under binding domain `v2`. It checks local continuity before and after each operation, including upload parts and download iterations. Request construction is lazy, so a failed precheck prevents polling the operation. Tests cover zero management hash, ambiguous/unconfirmed authorization, missing/replaced keys, same-key success, and changes during awaited work. Vendor provenance records are updated; immutable upstream hashes remain unchanged.

**Compatibility:** old adapter-derived `v1` identities do not automatically match `v2` files. Never bypass the owner/AAD check by rewriting a label. See [integration boundaries](../integration-boundaries.md).

### A02 — Establishment crossed caller identity changes

**Impact:** high; a handshake could dispatch or publish state under an outdated owner identity.

`request_chat` and `accept_chat` captured ownership before awaiting DH configuration and remote RPCs without checking the same ownership at every publication boundary. Controlled transports changed identity during those awaits. The fix checks the captured caller identity before the remote mutation and before returning pending or established state. Positive fixtures perform real DH agreement and message crypto. Cancellation after dispatch remains an explicitly documented ownership limit of the initial in-memory exchange; no durable handshake journal is advertised.

### A03 — Direct text encryption could emit an oversized frame and consume sequence state

**Impact:** medium; a locally accepted message became undeliverable.

`EstablishedChat::encrypt_text` checked text size but omitted wrapper, header, and padding overhead. Its nominal-limit input produced a frame beyond `MAX_ENCRYPTED_FRAME_LEN` and advanced the outgoing count. The fix checks the complete ciphertext before incrementing the count. Regression tests verify refusal, unchanged sequence, a valid nearby size, and successful subsequent delivery.

### A04 — Receive state became live before its durable checkpoint succeeded

**Impact:** high; retrying a message after a storage error could return no message.

A real file-store lock prevented saving an authenticated incoming frame. The previous manager still advanced RAM state; after releasing the lock, retrying the same frame returned `[]` instead of the message. A crate-private synchronous `ChatCheckpoint` now saves candidate protocol and outbox state under the existing per-chat state lock before live publication. Ordinary save refusal preserves retryable state. The checkpoint callback does not take an async snapshot lock or introduce a new public `'static` requirement. Registration is serialized, and existing inline-response/reentrancy tests continue to run.

### A05 — Response errors and cancellation hid already accepted batches

**Impact:** high; an accepted gap-filling batch disappeared behind response I/O.

After receiving a later message and then the missing earlier message, a failed or canceled service response could hide both accepted messages. Repeating the ciphertext, including after reopening the encrypted file, returned an empty batch.

Protocol state and a bounded `pending_deliveries` journal now commit together. Each receipt records the exact input ciphertext digest, optional ingress order, and complete accepted batch. Plain receive recovers an interrupted call using that identity and settles its receipt synchronously before returning successfully. Failed response RPCs retain their exact outbound obligation without hiding accepted messages. Both message-count and serialized-byte budgets refuse work before consuming protocol state. A larger-budget reopen can resume preserved work.

This is not an exactly-once transaction with an application's external effects. An application needing explicit post-effect settlement should use Strong mode.

### A06 — Strong apply/replay lost the result before consumer ACK

**Impact:** high; stored ciphertext remained pending but its decoded result disappeared.

Three baseline regressions reproduced repeated apply returning an empty batch, restart replay losing an unacknowledged message, and restart losing both messages released by a sequence gap. Strong mode now retains the receipt and returns the same accepted batch until explicit consumer acknowledgement. ACK commits the contiguous ingress cursor before removing covered receipts. A cleanup failure is retryable without undoing the cursor or redelivering settled work. Existing raw-consumer ACK remains supported. Tests cover the three original failures, receipt budgets, and failure after cursor commit but before receipt cleanup.

### A07 — Restored protocol state could install impossible replay, gap, or counter metadata

**Impact:** medium to high for recovery correctness; these are local checkpoint integrity failures, not an encrypted-store authentication bypass.

A checkpoint with a pending-key identity for sequence `0` but no pending frame opened successfully and silently dropped the first authentic message as a replay. Other accepted inconsistencies included missing key provenance, duplicate pending frames, malformed wrappers, contradictory gap metadata, a recovery window beyond live limits, and a peer ACK ahead of the sent count. Review also found counters beyond the signed `i32` wire range; those made every representable incoming frame appear old.

`PersistedProtocolState::validate` is called by both record validation and runtime import before state installation. It checks counter bounds and ACK ordering, a one-to-one relationship between buffered frames and key identities, held-key/cutover provenance, and coherent gap/resend metadata. The sequence module reuses the live wrapper, ordering, neighbor, and window checks without silently deduplicating stored records, and enforces byte bounds before decoding. The final count after the last wire index remains legal (`1,073,741,824`); a decoded peer ACK cannot exceed `1,073,741,823`.

Positive tests reopen and drain a valid gap, preserve the final representable count, and reopen both real persistent peers throughout a complete DH rekey exchange before exchanging new-key messages and recovering a new-key gap.

### A08 — Memory storage swallowed transient suspension errors

**Impact:** medium; memory and file backends disagreed about successful policy changes.

`MemoryStorage::mark_transient_suspended` discarded the nested `Result` from `suspend_record`. Invalid IDs, persisted IDs, and duplicate markers reported success. Propagating both result layers makes its refusal behavior match file storage. Direct backend parity tests cover these cases and valid insertion.

### A09 — Transient messages used a stale TTL cache

**Impact:** medium; outgoing message metadata contradicted the current conversation state.

After an authenticated peer `SetMessageTTL(17)`, a transient manager's next ciphertext still encoded TTL `0`. The separate TTL map was replaced with an active-identity set; outgoing TTL comes from the authoritative protocol state. Round-trip tests exercise `17`, reset to `0`, and `i32::MAX`. Application-side expiry remains the application's responsibility.

### A10 — Durable managers accumulated inaccessible duplicate RAM events

**Impact:** medium; duplicate plaintext could accumulate without a consumer drain API.

The embedded RAM manager emitted received-message, service, acknowledgement, and closure events even though persistent callers have no event-drain API for that queue. Checkpointed operations now use their bounded receipt path and suppress these inaccessible duplicate events. Public RAM-manager event semantics remain unchanged. A crate-level regression checks all affected event categories.

### A11 — Failed archive export left partial plaintext and blocked retry

**Impact:** medium; late validation/copy errors left an incomplete destination behind.

Tests reproduced failure after earlier output had already been written: an invalid later asset, a nonregular media source, and a media symlink escaping the allowed root. The exporter now creates a private sibling staging directory, builds the complete archive, and publishes only after success. RAII removes owned staging content on ordinary failure. Existing nonempty output remains untouched; reported paths refer to the final directory. Tests cover fresh and empty destinations, path suffixes, read-only source permissions, retry, and existing content preservation.

Windows removes only a verified-empty destination immediately before rename and attempts to recreate it if publication fails. That branch does not promise uninterrupted existence of the empty directory. Private parent directories are required; rename is not a physical power-loss durability guarantee, and newly created parent directories can remain.

### A12 — Forwarding references validated keys but not their location or size

**Impact:** medium; malformed references produced unusable forwarding descriptors.

The descriptor builder now requires a nonzero file ID, positive DC ID, and a nonzero declared plaintext size whose computed padded size fits the transport's local ceiling, together with key/IV fingerprint validation. Valid negative signed file IDs and access hashes remain supported. The local ceiling does not describe every account's server-side upload allowance; Telegram documents configurable upload part limits.

### A13 — Voice detection accepted truncated Opus identification data

**Impact:** low; arbitrary truncated input could be mislabeled as a voice note.

The detector recognized an eight-byte `OpusHead` prefix without the complete identification packet. It now validates first-page packet/lacing completeness, the identification header, compatible version/channel structure, and channel-map/stream constraints. Positive mono, stereo, and supported multichannel fixtures remain accepted. This is header classification, not full audio decoding or CRC validation.

### A14 — Autosave load/rewrite silently normalized stored information away

**Impact:** medium; authenticated history could lose records or unknown fields on an ordinary rewrite.

Synthetic AES-GCM files using the existing `KSCAUT01` format reproduced duplicate chat and message keys replacing earlier records, repeated enabled IDs collapsing, and unknown state/message/media fields disappearing after `start_auto_save(99)`. Each reproducer decrypted the actual rewritten file to establish loss. Numeric aliases and inconsistent indexes were already refused and are not new findings.

Strict private stored-record views now reject unknown fields and duplicate parsed identities before insertion. Public `SavedSecretMessage` and `SavedMediaRecord` Serde behavior, public methods, header/AAD/envelope, valid legacy optional fields, and documented duplicate insertion behavior remain unchanged. Rejected opens preserve exact ciphertext and release the writer lock.

## Review safeguards and documentation corrections

Review of the new checkpoint implementation caught a regression where failed tombstone persistence could undo mandatory local closure. The final code always closes and clears live state on fatal or explicit termination even if persistence fails, and retries tombstone persistence before a later discard. This was caught during repair and is not counted as another baseline finding. A real authenticated bad-parity frame and held file lock exercise the safeguard.

README, architecture, integration, and mode documents now distinguish media helpers from manager orchestration, caller-driven autosave from an automatic hook, saved plain-text/media export from full Desktop feature parity, and the consumer cursor from Telegram `qts`. Module links were corrected. Historical release entries remain historical; the `v0.4.0` dependency example is explicitly identified as predating these corrections.

## Limits that remain contractual

No live Telegram credentials were used. Synthetic transports, real crypto/files, offline vectors, and native CI do not substitute for a real-account interoperability run. Signing requires its separate protected release environment and was not invoked by this audit. Power-loss and external filesystem interference are not simulated guarantees. Failed mandatory closure cannot erase an older disk checkpoint while storage remains unavailable; successful later tombstoning is required before claiming durable closure. These limits are documented rather than represented as completed tests or new unfinished fixes.
