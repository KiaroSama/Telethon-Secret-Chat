## 3. Confirmed findings and implemented fixes

### R01 — High: previous shared keys were not confined to their incoming sequence interval

**Code:** `src/protocol/`, `src/ported/rekey.rs`. **Tests:** `tests/protocol_followup.rs`.

The receiver retained the previous shared key while a gap existed, but recorded neither a sequence cutover nor the key used for each buffered frame. Consequently, an authenticated previous-key frame could be accepted at a position after authenticated new-key traffic. A previous-key frame queued before the switch could also survive beyond it. A valid CommitKey did not constrain those queued positions. Conversely, a later gap containing only new-key traffic could unnecessarily retain the previous key and prevent another exchange.

The fix tracks bounded per-frame key provenance and the earliest authenticated incoming cutover. New-key traffic establishes the boundary; a matching delayed CommitKey can tighten it to the first following sequence. Validate both the arriving frame and already buffered frames before publishing messages or immediate actions. A contradiction closes the chat and clears retained protocol state. Preserve the accepted exchange identifier long enough to validate a delayed commitment after pending-key adoption. A matching commitment must itself authenticate with the preceding shared key, before or after implicit adoption. Retire the previous key once all positions before the cutover are processed, even if a later new-key gap remains. These defects require frames authenticated by a shared key the chat holds; they do not establish unauthenticated remote compromise.

**Acceptance:** previous-key frames after the boundary refuse; queued frames receive the same checks; legitimate preceding gaps recover; lost and delayed CommitKey paths validate exchange/fingerprint; initiator and acceptor confirmation remain correct; subsequent rekey is possible once preceding gaps are filled. Same-sequence pending duplicates must not hide contradictory key provenance. Processed duplicates and harmless same-key pending duplicates retain their specified behavior.

### R02 — Medium: buffered neighbors were not checked before immediate Resend effects

**Code:** `src/ported/sequence.rs`. **Tests:** `tests/protocol_followup.rs` and manager suites.

The sequence preflight checked a frame against the last processed acknowledgement and wrapper layer, but not against already authenticated pending neighbors. A Resend wrapper could therefore contradict a known future acknowledgement and still become an immediate action. The contradiction would only be detected later while draining the gap, after an effect had already escaped.

The fix compares a new frame with the nearest buffered predecessor and successor. Peer acknowledgement counters and wrapper layers must be nondecreasing in sequence order. Run these checks before exposing immediate actions. Existing sign, parity, future-acknowledgement, gap-window, and byte limits remain enforced. Capability announcements remain separate from chronological wrapper layers.

**Acceptance:** both neighbor directions, acknowledgement and wrapper-layer contradictions, valid monotonic gaps, and duplicate behavior are covered. Rejected Resend input exposes no immediate action and causes no manager replay or acknowledgement side effect.

### R03 — Medium: repeated authenticated messages could terminate a healthy chat during inner parsing

**Code:** authenticated receive guard and `src/ported/schema_secret_tl.rs`. **Tests:** `tests/protocol_followup.rs`.

The receiver fully decoded the inner TL object before recognizing an already processed sequence. A repeated authenticated wrapper with an altered or obsolete inner constructor could therefore produce a fatal parse error instead of being dropped. Telegram's sequence contract explicitly requires processed repetitions to be dropped without examining their inner contents.

The fix reads a bounded, authenticated wrapper header first. Required wrapper validity and counter sign/parity checks retain their existing behavior. An already processed sequence returns an empty batch before inner-object parsing. New sequences still receive the complete framing, schema, sequence, and key-lifecycle checks. Pending duplicate handling additionally preserves key-provenance consistency from R01.

**Acceptance:** malformed inner content at a processed position is ignored and the next valid message succeeds; new malformed content still refuses; wrong counter sign/parity remains fatal where required; invalid short nonce/unsupported header cases retain their established nonfatal refusal behavior. No unauthenticated header may advance state or trigger a response.

### R04 — Medium: a previously used custody handle could delete another authorization's replacement store

**Code:** `src/custody.rs`. **Tests:** `custody_stale_owner_cannot_delete_a_recreated_store`, `custody_owner_binding_survives_loading_and_cleanup`.

Cleanup authenticated the file with the encryption key but did not remember which authorization had used the handle. With two legitimate handles, one could delete owner A's file, a new handle could create owner B's file at the same path using the same storage key, and the stale A handle could then delete B's replacement. Loading or reusing a handle could also silently switch its authorization.

The fix binds a handle to the authorization of its first successful save/load/owned cleanup, using `OnceLock<String>` for the shared-reference load API. Every later complete-store validation and mutation checks that binding. Cleanup does not reset it. Open a new handle for an intentional owner change. The authenticated file format is unchanged.

**Acceptance:** stale cleanup preserves the replacement bytes, loaded handles cannot switch owners, cleanup cannot reset a saved handle's owner, and existing same-owner save/load/cleanup tests remain green. This is a handle-identity correction, not a claim of protection from a hostile OS account controlling the directory.

### R05 — Medium: an encrypted data file could also be accepted as a lock sidecar

**Code:** `src/storage_file.rs`. **Test:** `an_authenticated_store_cannot_be_reused_as_another_stores_lock_file`.

A caller could place one encrypted store at another store's `.lock` path. The lock helper accepted that nonempty regular file. Since data-store writes atomically replace their inode, a cooperating writer could replace what another writer considered its stable lock file, defeating coordination.

The fix acquires the sidecar lock and then requires the locked file to remain empty before treating it as a coordination file. A nonempty file refuses without replacing or deleting its contents. Existing regular-file, symlink, permissions, exclusive-creation, and persistent-sidecar rules remain intact.

**Acceptance:** a real authenticated store at the sidecar path is preserved byte for byte; the other data file is not created; normal empty-sidecar coordination and existing lock/contention tests pass.

### R06 — Medium: ingress restoration silently normalized ambiguous identities and accepted impossible stream state

**Code:** `src/ingress.rs`. **Tests:** `tests/storage_followup.rs`.

Default map/set deserialization collapsed duplicate stream keys, duplicate pending order keys, or repeated replay orders before semantic validation could inspect them. A duplicate pending stream could discard an owed record; a duplicate replay stream could discard replay history. Numeric order aliases such as `1` and `01` could resolve to the same identity. Separately, empty pending-stream maps absent from replay history passed restore validation. At the stream ceiling, a subsequent successful capture could write a snapshot that the same configuration could no longer reopen.

The fix uses explicit map visitors and a checked replay-order collection to reject duplicates while parsing, before values are overwritten. Validate typed order identity rather than only key spelling. Reject empty replay streams and empty/untracked pending streams that current writers never produce. Keep the serialized schema, signatures, existing valid stores, and finite limits unchanged.

**Acceptance:** all duplicate map/set layers and numeric aliases refuse; invalid orphan streams refuse without publication. A separate positive fixture restores exactly `4096` nonempty tracked streams, captures into an existing stream, and reopens with the owed payload and identity intact. Ordinary capture, exact duplicate handling, explicit acknowledgement, and restart contracts remain green.

### R07 — Medium: an empty destructive ingress drain bypassed stale-state checks

**Code:** `DurableIngressController::drain_in_order`. **Test:** `empty_ingress_drain_refuses_a_stale_snapshot`.

The empty-result fast path returned success without checking whether another controller had committed newer obligations. A stale controller could report that a stream had nothing left to drain while the current durable snapshot contained a new pending record. Invalid storage could also appear healthy through this path.

The fix calls the store's existing current-revision check before returning an empty destructive-drain result. Non-consuming `pending_in_order` remains a local snapshot inspection API. Nonempty drain continues to persist a candidate before adopting it.

**Acceptance:** a stale empty drain refuses and preserves the newer snapshot bytes; reopening shows the owed record. A directory/unavailable store does not report a successful durable drain. Valid empty drains and all previous drain/acknowledgement failure tests remain supported.

### R08 — Medium: malformed schema declarations could replace a valid generated manifest

**Code:** `src/ported/tool_generate_schema.rs`. **Test:** `malformed_schema_fields_and_results_do_not_replace_the_manifest`.

The checked native schema path validated constructor names/IDs and the presence of a result, but accepted malformed fields and result syntax. For example, a field with no type was accepted and the command replaced the existing manifest. Other cases included empty vectors, invalid flag references/bit numbers, duplicate field names, and extra terminators.

The fix validates qualified identifiers, unique named fields, preceding `#` flag declarations, flag bits `0..31`, nested `Vector`/`vector` types, and result syntax before generation. Nested vector validation is iterative. Preserve the historical permissive adapter only for its explicitly separate differential-replay API. The native command refuses unsupported general TL combinator syntax instead of pretending to parse it.

**Acceptance:** malformed inputs exit with failure and preserve the previous output bytes; supported namespaces, nested vectors, flag bit `31`, and the tracked schema generate/check successfully. This maintenance manifest validator is not advertised as a compiler for every form of TL grammar.

### R09 — Medium: source inventory allowed tracked private runtime files

**Code:** `.github/scripts/validate-source.sh`. **Tests:** the Unix source-inventory cases in `tests/ci_followup.rs`.

The source gate relied partly on ignore rules while validating only selected build/cache paths. Ignore rules do not exclude files already tracked or deliberately force-added. A tracked session file could pass the gate and be included by `git archive`. The reproduction used synthetic canaries; the audit did not find or publish a live credential leak.

The fix rejects case-insensitive live environment, session/journal, and key/certificate-container filename patterns in the tracked inventory. Public `.env.example`, `.env.sample`, and `.env.template` files remain deliberate exceptions. Logs report escaped paths and never print the canary contents. This filename policy complements Gitleaks; it is not a replacement for content scanning or a classifier of arbitrary files.

**Acceptance:** force-added `.env.live`, session, session-journal, PFX, and key fixtures fail before source packaging; public templates pass. The source-archive/exact-revision consumer/install job and Gitleaks must pass on the final head.

### R10 — Medium: the open Jiff upgrade PR did not compile and omitted vendor provenance updates

**Code:** vendored `grammers-client` manifest, HTML parser, root workspace lockfile, and local patch manifest. **Tests:** vendored HTML timestamp parsing and transport provenance checks.

[Dependabot PR #50](https://github.com/KiaroSama/Grammers-Secret-Chat/pull/50) upgrades the vendored client's separate Jiff dependency from `0.2.40` to `1.0.3`. The root crate already used Jiff 1.x; that did not upgrade the vendored client. The dependency-only PR fails with Rust `E0599` because `DateTimeParser::parse_zoned` was renamed in Jiff 1.x. Its changed vendor manifest also requires a corresponding local-patch provenance entry. Re-fetching main or changing the release version cannot repair either issue.

The follow-up audit PR incorporates the intended upgrade completely: use `parse_zoned_datetime`, retain timestamp behavior, update the root workspace lockfile's client-to-Jiff dependency edge without unrelated version/checksum churn, and update the distributed-source hashes and vendor documentation. Standalone vendor lockfiles do not contain the changed client dependency and remain unchanged. Preserve `upstream-hashes.json` as the immutable upstream baseline. Additional parser tests exercise named-zone/offset conflicts, DST folds and gaps, UTC/offset fallbacks, and invalid dates.

**Acceptance:** the dependency-only reproducer fails with the same missing-method error as PR #50; the corrected vendor builds and its unit/doc tests pass; the original and new HTML timestamp cases pass; root tests and provenance checks pass. After the audit PR is integrated, the authorized reviewer must verify that PR #50's intended upgrade is included and close it as superseded under the Rules, or repair/integrate it equivalently. ## 4. Previously fixed behavior verified without another production rewrite

The existing manager fixes passed all original tests and three additional deterministic transport schedules in `tests/manager_followup.rs`:

- A Resend received while the original RPC is in flight survives that RPC's successful completion, and the same ciphertext is replayed.
- Peer acknowledgement does not erase an independently owed replay when the original RPC later fails. Explicit retry sends the original bytes once and settles the obligation.
- Re-delivery of the identical authenticated Resend during a blocked replay does not create a third transmission or a duplicate acknowledgement event.

These tests inspect actual captured frames, reserved counters, retry counts, and emitted events, with timeouts for deadlock detection. They verify already working behavior; they are not counted as additional discovered bugs. No manager production change was needed for these schedules.

The earlier cryptographic vectors, malformed frame/TL cases, key lifecycle tests, storage failure/atomic replacement tests, export goldens, public API boundaries, and vendor pin checks remain required gates. The retired launcher stays removed.
